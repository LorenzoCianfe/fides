## [Unreleased]

### Added

- **Phase 1 Slice 8 Wave A — client token transport and web hardening (ADR-0027).** An **opt-in, per-request** httpOnly-cookie transport for the browser client, closing the gap ADR-0021 deferred to this slice. A client sends `X-Fides-Token-Transport: cookie` on the three routes that mint or rotate a session; everything else, including an absent header, keeps the exact Phase 1 bearer contract. Transport is negotiated per request rather than per deployment because web and mobile share one API instance — a global switch could not express "cookies for this client, bearer for that one", and user-agent sniffing would have silently changed existing behaviour. All 219 pre-existing tests pass unmodified, which is the evidence the negotiation is genuinely additive.
- Cookie mode **withholds the tokens from the response body** (`accessToken`/`refreshToken` are now optional in the contract): setting cookies *and* echoing the tokens would hand them back to script and buy nothing. The pair is `httpOnly` and `SameSite=Strict`; the access cookie is scoped to `/v1` while the **refresh cookie is scoped to `/v1/auth/refresh`**, so the longest-lived credential is simply absent from ordinary API traffic.
- **CSRF defence by double-submit token bound to the session row** (migration `0011`): a random `fcs_` token whose SHA-256 is stored on the session and whose plaintext is returned in a deliberately readable cookie, echoed back in `X-CSRF-Token` and compared in constant time. Hashing a random token rather than deriving an HMAC keeps this consistent with how every other secret is held (ADR-0020), adds no server-side signing key to configure or rotate, and revokes the CSRF token with its session. Bearer callers are **exempt** — a header that must be set explicitly is not an ambient credential. A session issued in bearer mode holds no hash and therefore cannot be driven from a cookie at all: the check **fails closed** rather than opting out.
- **Refresh enforces CSRF inside its own rotation transaction**, not in the guard. Refresh deliberately runs on an expired access token and so cannot sit behind `SessionAuthGuard`, which would have left it the one cookie-driven, state-changing hole in the design — a cross-site page could churn a victim's token pair and strand the real client on a superseded token. The check runs against the row already held `FOR UPDATE`, ordered *after* reuse detection so a stolen token still trips the alarm, and *before* anything rotates.
- **Security headers via helmet.** HSTS at two years with `includeSubDomains` and `preload`, emitted unconditionally (browsers ignore it over plain HTTP, so it is free locally and correct the moment TLS terminates). The JSON surface gets `default-src 'none'; frame-ancestors 'none'; base-uri 'none'` because it genuinely needs to load nothing; the inline-script relaxation Swagger UI requires is **scoped to `/docs` alone** rather than loosening the policy over the money-moving surface. `Cross-Origin-Resource-Policy` is `cross-origin`, since CORS rather than CORP is the control that governs a cross-origin JSON API. CORS becomes credentialed with an explicit request-header allowlist.
- **Native passkey app association served by the API**: `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`, generated from configuration and excluded from the `/v1` prefix (their paths are fixed by Apple and Google). Serving them from the API means the association follows whichever HTTPS origin fronts it — a production domain or a developer's tunnel — with no second deployment to keep in step, which is what makes native passkeys both shippable and locally testable on a device. Unset configuration yields 404 rather than an empty document, because an association listing no apps fails silently and undiagnosably on device.
- A dependency-free `Cookie:` header reader (`shared/http/cookies.ts`) rather than taking `cookie` plus `@types/cookie` to read three known names — following the precedent of the in-house TOTP and scrypt helpers (ADR-0025). It returns a null-prototype object on purpose: assigning a parsed name like `__proto__` onto a plain object literal would mutate the prototype instead of creating an own property.
- Tests (260 total, +41): the cookie parser's sharp edges including the prototype-pollution case; guard-level coverage of transport preference, malformed-bearer non-fallthrough, per-method CSRF enforcement, and the fail-closed bearer-session case; and an HTTP integration suite driving cookie issue, attribute scoping, cookie-only authentication, CSRF rejection and acceptance, cookie-driven refresh with and without a token, logout cookie clearing, the security headers on both the API and `/docs`, and the association documents.
- New settings: `COOKIE_SECURE`, `COOKIE_SAMESITE`, `IOS_APP_ID`, `ANDROID_PACKAGE_NAME`, `ANDROID_CERT_FINGERPRINTS`. Configuration rejects `COOKIE_SAMESITE=none` without `COOKIE_SECURE=true` (browsers silently drop that pair) and a half-configured Android association.

### Security

- **Dependency audit gate returned to green (ADR-0026).** The blocking `pnpm audit --prod --audit-level=high` check had been red on `main` since CI last ran on 2026-07-05, reporting 34 advisories of which 15 were high — none caused by Phase 1 code, all against packages carried by the Phase 0 client shells. Ten distinct high-severity advisories are now closed: three in `next` (a Server Actions denial of service and two server-side request forgeries), two in `postcss` (arbitrary file read and path traversal via `sourceMappingURL`), one in `sharp` (inherited libvips CVEs), one in `js-yaml` (quadratic CPU via merge-key chains), and three in `brace-expansion`.
- `next` moved to `^15.5.22` in `apps/web` and `apps/admin` — a patch-level move inside the pinned major, so the "framework majors deferred to Phase 7" decision is untouched. `postcss`, `sharp`, and `js-yaml` are transitive and pinned by intermediates that have not released fixes, so each is closed with a `pnpm` override keyed on the advisory's own vulnerable range rather than a bare package name. The scoping is load-bearing for `js-yaml`: the tree also carries `3.15.0` under `cosmiconfig`, and an unscoped override would have dragged it across the 3→4 boundary that removed `safeLoad`.
- **`brace-expansion` is forced to `5.0.8` and patched.** Its out-of-memory advisory declares a vulnerable range of `<=5.0.7`, so no version in the 1.x or 2.x lines can clear it — not even `2.1.3`, which actually ships the fix but still matches the range. `5.0.8` is the only clearing version, and `brace-expansion@4` had removed the callable default export that `minimatch@3`, `@5`, and `@9` depend on (verified by execution: three of the four `minimatch` versions in the tree break under an unpatched force). A single patch on `brace-expansion` restores the callable default in both the CommonJS and ESM entries, leaving the named exports `minimatch@10` uses untouched — one patched package instead of three rewritten consumers. The override pins `5.0.8` exactly, because pnpm 9 keys patches by exact version and a silent drop of the shim would be worse than a loud failure.
- **No new audit suppression was added.** The single pre-existing `ignoreGhsas` entry (`GHSA-r5fr-rjxr-66jc`, `lodash` `_.template` code injection reaching `apps/api` via `@nestjs/swagger`) stays, because its declared patch target `lodash >= 4.18.0` has never been published. Since pnpm counts suppressed advisories in its summary but excludes them from the exit code, the gate still tallies one high while exiting zero — the exit status is the signal. `security.md` §9.1 now writes the remediation order down as policy.
- Two corrections to `docs/phase-1-handoff.md` §8, which recorded the advisory set inaccurately: `postcss` had since joined it, and the claim that no advisory is reachable from `apps/api` does not hold for `js-yaml`, which arrives through `@nestjs/swagger`, a production dependency of the API. `sharp` also enters via `next`, not Expo.
- Verified after the change: the audit gate exits zero (and still exits non-zero at `--audit-level=moderate`, confirming the gate reacts rather than always passing), `pnpm install --frozen-lockfile` is clean, all four `minimatch` versions expand braces correctly, and lint, typecheck, and build pass for every package alongside the full `apps/api` suite at 219/219.

### Added

- **Phase 1 Slice 7 — admin RBAC, MFA, and four-eyes (ADR-0025).** A new `admin` module gives the back office its own identity: a separate `admins` table with its own guard, principal, session table, and token prefix (`ast_`), sharing no table and no code path with customer authentication — so no customer-facing authorization defect can reach the back office, and `assertResourceOwnership` keeps a single, customer-only meaning. Admin authorization is by capability, never ownership.
- Two-step, two-factor login (migration `0010`): a correct password returns only a single-use, five-minute hashed **login challenge**, never a session; the session is issued solely after an RFC 6238 TOTP code verifies. Passwords use scrypt from `node:crypto` in a self-describing `scrypt$N$r$p$salt$hash` format, so work factors can be raised without a migration, and failures are uniform and constant-time across unknown, disabled, and wrong-password admins. TOTP is a minimal in-house implementation over `node:crypto` — unit-tested directly against the RFC 6238 vectors (SHA-1/256/512) and the RFC 4226 HOTP vectors — with a strictly-increasing accepted time step, so a code cannot be replayed even inside its own validity window. The seeded admin carries no secret: it is generated at first login, returned exactly once, and activated only when a code minted from it verifies.
- Back-office sessions: one opaque 256-bit token stored only as a SHA-256 hash, with a **30-minute sliding idle window** and a hard **8-hour absolute cap** (env-tunable). Deliberately no refresh/rotation pair — at a 30-minute idle window the sliding deadline is the whole policy. Every request validates against the row, so revocation and disablement take effect immediately; dead sessions and spent challenges are purged by a new `AdminSweeper` on the existing retention interval.
- RBAC through a code-defined `PERMISSIONS_BY_ROLE` matrix over the five ADR-0011 roles, enforced by a `@RequirePermission` guard that fails closed when a route declares no permission. **Segregation of duties is structural, not conventional:** `admin_funding.request` belongs to the compliance officer and support agent, `admin_funding.approve` to the super-admin alone — which is deliberately denied the request half — so no role holds both. A unit test asserts that as an invariant over the whole matrix, so widening a role until it can self-approve fails the build; a runtime `checkerId != makerId` check and a database CHECK constraint back it up.
- **Four-eyes proven end to end on real money.** A generic `pending_admin_actions` queue with exactly one registered type (`admin_funding`) — the shape already fits the Phase 2/3 actions. A maker files a request and nothing moves; a differently-roled checker approves it, and the credit posts **inside the same transaction that transitions the request out of `pending`**, under a row lock, via a new `onAuthorize` hook on the funding service. A concurrent double-approval cannot post twice, a failed posting leaves the request pending rather than approved-but-unexecuted, and a retry carrying the original `Idempotency-Key` replays the first result rather than being rejected. Requests expire after 24 hours. Four-eyes *breadth* (suspension, reversal, card freeze) is deferred to Phase 2/3 with the actions it would govern.
- Read-only views: the customer directory and detail (KYC status, accounts, wallets, live balances), any wallet's transaction history (capability-scoped rather than ownership-scoped), a ledger account beside its recomputed reconciliation state — making the ADR-0019 invariant operable rather than test-only — and the **audit read and verification surface Slice 6 deferred**, behind `audit.read` (auditor or higher; the support agent does not hold it). The `audit_actor_type` enum gained the `admin` value the Slice 6 schema anticipated, and every admin action is recorded on the tamper-evident trail.
- A minimal staffing surface (`admins.manage`, super-admin only): create, list, and disable operators. Included because four-eyes is not a control a single operator can exercise — seeding creates one admin, and the matrix denies that admin the maker half, so without this the workflow would be unstaffable outside tests. Disabling is immediate offboarding, and an admin cannot disable their own account.
- Tests (219 total, +90): RFC-vector TOTP and base32 units, scrypt format and verification units, the segregation-of-duties matrix invariant, service-level integration for bootstrap seeding, the two-factor flow, code replay, challenge single-use and expiry, session sliding/clamping/expiry/revocation, staffing, and retention; plus an HTTP suite driving the real journey — first-login enrolment, token-namespace isolation between customer and admin, per-role RBAC denials, the read views, and the full four-eyes funding journey with balance movement, ledger zero-sum, idempotent replay, self-approval rejection, and an intact audit chain.

### Changed

- **The dev funding faucet is retired (ADR-0025, closing the ADR-0023 gap).** `POST /v1/dev/funding`, its contracts, and the `DEV_FUNDING_ENABLED` / `DEV_FUNDING_MAX_MINOR` settings are gone: a customer can no longer credit their own wallet by any route. The posting logic stays in the payments module, where the ledger integration lives, but now takes an explicit target wallet and an admin actor rather than crediting the caller from their own session — the admin module owns the workflow and calls into it, so money movement keeps a single implementation. The kill-switch is gone because authorization now comes from role, four-eyes, and audit; the per-request cap remains as a blast-radius limit, renamed `ADMIN_FUNDING_MAX_MINOR`. Amount and target rules moved to a shared `validateRequest`, applied both when a request is filed and when it executes.
- New settings: `ADMIN_BOOTSTRAP_EMAIL`, `ADMIN_BOOTSTRAP_PASSWORD` (consumed only when no admin exists at all, so configuration cannot add or reset an operator once the back office is live), `ADMIN_SESSION_IDLE_TTL_MS`, `ADMIN_SESSION_ABSOLUTE_TTL_MS`, and `ADMIN_FUNDING_MAX_MINOR`.

- **Phase 1 Slice 6 — append-only, hash-chained audit trail (ADR-0024).** A new `audit` module records every sensitive action to an immutable, tamper-evident `audit_log` (migration `0008`), written **inside the audited action's own transaction** so an action can never exist without its audit, nor the reverse. Each row is chained — `hash = sha256(prev_hash + canonical(record))` over its immutable fields, with a gap-free `seq` — under a transaction-scoped advisory lock acquired last in the transaction, forming one global chain whose integrity a pure `verifyAuditChain` walk confirms (the analogue of the ledger's reconciliation invariants). The same `fides_forbid_mutation` triggers as the ledger reject UPDATE/DELETE at the database, so any out-of-band edit or deletion of a past record breaks the chain and is caught by verification.
- Six sensitive actions are wired, each appended in the transaction that already exists (nothing moves off the outbox): the P2P transfer and dev funding — via a new symmetric `onPosted(tx, now, result)` hook on `PostEntryCommand` (the mirror of Slice 5's `onClaimed`, run after all ledger writes so the chain lock is held for the shortest possible tail, and first-execution-only so an idempotent replay adds no record); SCA step-up grant issuance; session revocation and refresh-reuse revocation; and event-driven account provisioning (a `system` actor, inside the dispatcher transaction). Records carry internal references only — user, wallet, and journal-entry ids, amounts, and action hashes — never raw PII, since the trail is immutable and un-erasable; `before`/`after` is recorded only for mutations of mutable state (a session revocation), while a money move targets the already-immutable journal entry. The request correlation id is threaded from each controller onto the record.
- Retention tightened (ADR-0024 revisits ADR-0021): dead sessions are now **purged promptly** rather than kept for a 90-day forensic grace, because their revocation and reuse events now live in the tamper-evident trail (with session, device, reason, and timestamps). The SCA-grant → session foreign key became `ON DELETE CASCADE` (migration `0009`), so an outstanding grant is removed together with its purged session; the audit table itself is exempt from the sweeper and protected by the append-only triggers.
- Tests (129 total): pure break-detection over crafted chains (field modification, forged hash, deleted middle record, reordering, detached genesis); integration for the append/verify happy path, atomic rollback with the caller transaction, append-only trigger rejection, out-of-band tamper detection (the chain catches an edit made with the trigger disabled), and idempotent replay writing no duplicate record; plus wired-seam assertions on provisioning (a `system` record) and the full HTTP transfer (correlation id captured, whole-journey chain intact).

- **Phase 1 Slice 5 — internal instant P2P transfer + dev funding (ADR-0023).** `POST /v1/transfers`: a session-guarded, idempotent (`Idempotency-Key` header), SCA-gated transfer that debits the sender's wallet and credits the recipient's in one balanced journal entry (sender guarded against overdraft). PSD2 dynamic linking is enforced against the *executed* parameters — the action hash is recomputed server-side from the amount and payee and the single-use grant is consumed inside the posting transaction, so a tampered amount or payee fails with the generic authentication error. This proves the Phase 1 exit criteria end to end: value moves between two users, balances reconcile, and the whole ledger nets to zero.
- The transfer weaves SCA into the money path via a new optional `onClaimed(tx, now)` hook on `PostEntryCommand`: `PostingService` runs it after a successful idempotency claim and before any ledger write, so the grant is consumed **exactly once** — an idempotent replay returns the stored result without re-consuming or re-posting, and any in-transaction failure rolls the claim and the consumption back together. A shared `buildTransferScaAction` in `@fides/contracts` builds the canonical `{ type, payload }` both the client signs and the server rebuilds, eliminating drift.
- Recipient identified by email (resolved server-side to the recipient's EUR wallet); self-transfers and non-EUR amounts are rejected. Idempotency is scoped per actor with a request fingerprint over the linked parameters (`recipient`, `amount`, `currency`), so key reuse with different money is a 409 while a genuine retry (which may carry a fresh grant) replays.
- Dev funding faucet `POST /v1/dev/funding` (ADR-0023): credits the caller's own wallet from `system:settlement` (asset, unguarded) with a balanced entry — session-guarded, idempotent, amount-capped, and gated by `DEV_FUNDING_ENABLED` (off by default; 404 when disabled). No SCA, since crediting one's own wallet is not a PSD2 payment. A development affordance until admin RBAC (Slice 7).
- Wallet transaction-history read `GET /v1/wallets/{walletId}/transactions` (ADR-0023): ownership-scoped and keyset-paginated over `(occurred_at desc, journal_entry_id desc)` from the `transaction_history` projection, exposing each entry's signed amount and running balance. The wallet balance stays on the account resource (no separate balance endpoint). Backed by a new `TransactionHistoryReader` and an internal `WalletResolver` (kept in the accounts module, which owns wallet ownership).
- HTTP integration suite driving the real step-up ceremony over supertest: the two-user funded transfer with balance movement and ledger zero-sum, idempotent replay, dynamic-linking tamper rejection, single-use grant enforcement, overdraft rejection, self-transfer and missing-key rejection, funding cap, ownership-scoped paginated history, and OpenAPI presence — 115 tests total. No new migration (every table already existed); adds `DEV_FUNDING_ENABLED` and `DEV_FUNDING_MAX_MINOR`.

- **Phase 1 Slice 4 — accounts & wallets (ADR-0022).** Event-driven account provisioning: a `kyc.approved` handler registered in the outbox dispatcher creates one EUR account, a single EUR wallet, and the wallet's backing ledger account (`wallet:<walletId>`, liability) via `LedgerStore.createAccount`. It runs inside the dispatcher's transaction (so ledger account, account, wallet, and the dispatch marker commit atomically) and is idempotent under at-least-once delivery — the account row is inserted first with `ON CONFLICT (user_id) DO NOTHING`, so a redelivery short-circuits before any ledger account is created and leaves no orphans. The `kyc.approved` backlog that accrued since Slice 3 drains on the first dispatch.
- Account read surface under `/v1/accounts` (ADR-0022): `GET /v1/accounts` (principal-scoped list) and `GET /v1/accounts/{accountId}` (ownership-checked — unknown id → 404, another user's id → 403). Each wallet's balance is read live from the authoritative ledger `balances` projection (ADR-0019); no balance is stored in the accounts module. Follows the Wave C controller conventions (`SessionAuthGuard`, explicit `@Inject` tokens and `ZodValidationPipe`, Zod-first contracts with a colocated OpenAPI registrar).
- `accounts` and `wallets` tables (migration `0007`): one account per user (unique `user_id`), one wallet per currency per account, and a 1:1 wallet↔ledger-account binding. `LedgerStore.createAccount` gained an optional `executor` parameter so it can enlist in a caller's transaction (mirroring `SessionService.issueSession`). The `kyc.approved` event now carries a typed payload in a colocated `kyc-events` module.
- The `/v1/auth` HTTP surface (Slice 3 Wave C, ADR-0021): registration, email-keyed verification and resend (uniform anti-enumeration failures; verification returns the userId and a fresh enrolment token so onboarding resumes on any device), WebAuthn registration/authentication ceremonies, session refresh, logout, and per-device session list/revoke. Zod request contracts live in `@fides/contracts` with colocated OpenAPI path registrars; the generated document (with bearer security scheme) is served at `/docs`.
- SCA step-up seam with PSD2 dynamic linking (ADR-0021): an `sca` WebAuthn ceremony whose challenge is bound to the canonical hash of the action (recursively key-sorted JSON), minting a single-use, session-bound `fsg_` grant (hashed at rest, 5-minute TTL) that the Slice 5 transfer will consume atomically. Migration `0006` adds the ceremony type, `action_hash`, and `sca_grants`.
- Platform HTTP policy (ADR-0021): global `/v1` prefix (liveness stays at `/health`), correlation-id middleware (honors well-formed inbound ids, else UUID v7; echoed and injected into the error envelope), env-driven CORS allowlist, fail-fast `DATABASE_URL` with pool shutdown on close, and error-envelope mappings for rate limiting (`RATE_LIMITED`) and Zod validation issues.
- Auth rate limiting via module-scoped `@nestjs/throttler` (per-IP: register 5/min, resend 3/min, refresh 30/min, default 10/min) with a `THROTTLE_ENABLED` kill-switch honored on every route.
- Background operations: the outbox dispatcher and an ADR-0021 retention sweeper (prompt purge of consumed/expired challenges, enrolment tokens, email verifications, and SCA grants; dead sessions kept 90 days for forensics) run on env-tunable, overlap-guarded intervals behind `SCHEDULERS_ENABLED`. The dispatcher now only claims event types with a registered handler, so `kyc.approved` stays pending for Slice 4 account provisioning.
- Session listing (`SessionService.listSessions`) exposing device metadata and never token material; `SessionAuthGuard` wired to the protected routes with explicit injection tokens (the vitest/esbuild transform emits no decorator metadata, so DI and validation pipes are bound explicitly).
- HTTP integration suites driven by the software authenticator over supertest: the full register → verify → enrol → login → step-up → refresh → revoke → logout journey, error-envelope and anti-enumeration checks, correlation-id semantics, versioning, OpenAPI serving, throttling, and armed-scheduler behaviour — 95 tests total.

- **Phase 1 — Walking skeleton (in progress).** Ledger domain core: account taxonomy with normal-balance rules, positive-amount postings, and a balanced-by-construction `JournalEntry` builder (debits equal credits per currency), covered by example and property-based (`fast-check`) invariant tests.
- Ledger persistence: `ledger_accounts`, `journal_entries`, `postings`, a synchronously-maintained `balances` projection (ADR-0019), and a per-actor `idempotency_keys` table. A migration installs database triggers that forbid UPDATE/DELETE on the append-only ledger tables.
- Transactional posting service: posts a balanced entry, updates the balance projection under a deterministic row lock, enforces non-negative wallet balances, claims the idempotency key, and enqueues a `ledger.entry.posted` outbox event — all in one transaction. Read-side reconciliation (projection equals the sum of postings) and a whole-ledger zero-sum check.
- Outbox dispatcher and a denormalized `transaction_history` read model projected asynchronously from `ledger.entry.posted` (at-least-once delivery via `FOR UPDATE SKIP LOCKED`, idempotent on `(account, entry)`), carrying each account's signed amount and running balance.
- Identity onboarding foundation: natural-person registration (`users`, email verification via the `NotificationPort` console adapter, codes hashed at rest) and a KYC application behind a mock `KycPort` that auto-approves in development, emitting a `kyc.approved` event for downstream account provisioning.
- WebAuthn relying party (`@simplewebauthn/server`, ADR-0020): passkey registration and email-first authentication ceremonies with user verification required, attestation `none`, single-use hashed challenges (5-minute TTL) in Postgres, signature-counter clone detection, and decoy options for unknown emails so login cannot enumerate accounts. The first passkey is gated by a one-time enrolment token issued at email verification and auto-issues a session; additional passkeys require an authenticated session.
- Server-side sessions (ADR-0020): opaque 256-bit access/refresh tokens stored as SHA-256 hashes on a Postgres session row joined to the user on every validation (immediate revocation; suspended users cut off). Refresh rotates both tokens with reuse detection — presenting a superseded refresh token revokes the whole session. Lifetimes 15 m / 30 d idle / 90 d absolute, env-overridable. Client-declared device rows back per-device session listing/revocation.
- Session auth guard and resource-ownership assertion helper (object-level authorization), unit-tested; HTTP wiring follows in Wave C.
- A software P-256 authenticator test helper producing genuine CBOR attestations and ECDSA assertions, driving the full ceremony + session lifecycle integration suite (register → login → refresh → reuse-revocation → revoke, wrong origin/RP ID, UV and counter regressions, decoys, suspension).
- Testcontainers-backed integration tests running under `pnpm test` against an ephemeral Postgres with the committed migrations applied — covering the posting path, idempotency, append-only enforcement, reconciliation, and the async projection.

- **Phase 0 — Foundations.** Monorepo scaffolding (pnpm workspaces + Turborepo), strict TypeScript, ESLint (flat config) + Prettier, and a shared `@fides/config` package.
- Shared kernel `@fides/domain`: currency-safe `Money` value object (integer minor units, float-free rounding), currency registry, typed error taxonomy, and event/outbox primitives — unit-tested with Vitest (53 tests).
- `@fides/contracts`: Zod-first schemas as the single source of truth, with `zod-to-openapi` document generation.

### Security

The fixes are minor/patch bumps within the pinned majors and are the first task of Slice 8.
- Upgraded `drizzle-orm` to >= 0.45.2 to resolve a SQL-injection advisory (GHSA-gpj5-g38j-94v9) in the ledger ORM.
- Pinned patched transitive dependencies via pnpm overrides: `multer` >= 2.1.0 (DoS) and `glob` >= 10.5.0 (CLI command injection).
