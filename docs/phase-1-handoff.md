## 1. One-paragraph orientation

Phase 1 is built **backend-first** ("API + tests first, clients after"); with Slice 7 done, the backend is complete and only the clients remain. The double-entry **ledger** (Slices 1–2), the whole of **Slice 3** — identity onboarding (Wave A), WebAuthn relying party + server-side sessions (Wave B, ADR-0020), and the **`/v1/auth` HTTP surface with SCA step-up, throttling, and operational schedulers** (Wave C, ADR-0021) — **Slice 4** (accounts & wallets: event-driven idempotent provisioning off `kyc.approved` + the `/v1/accounts` read surface, ADR-0022), and **Slice 5** (the SCA-gated, idempotent internal P2P transfer, a kill-switched dev funding faucet, and the wallet transaction-history read, ADR-0023) are complete. **Slice 6** (the append-only, hash-chained audit trail, ADR-0024) and **Slice 7** (the back office: separate admin identity with password + TOTP, RBAC, shorter sessions, read-only views, and four-eyes on admin funding, ADR-0025 — which retired the Slice 5 faucet) are complete. Everything runs against a real Postgres via Testcontainers, including full HTTP journeys driven through supertest by a software authenticator producing genuine attestations and assertions — the transfer suite runs the real step-up ceremony end to end, and the admin suite runs the real two-factor sign-in and maker-checker approval end to end. `pnpm test` requires a running Docker daemon. ## 3. What is built

**Ledger** (`apps/api/src/modules/ledger`)
- `domain/` — account taxonomy with normal-balance rules; positive-amount `Posting`; `buildJournalEntry` (balanced by construction). `infra/` — `ledger_accounts`, `journal_entries`, `postings`, `balances` projection, `transaction_history` read model; `LedgerStore` (account creation, `Money` balance reads, reconciliation, zero-sum check).
- `application/posting.service.ts` — one transaction: idempotency claim → ordered `FOR UPDATE` balance locks → non-negative funds check on guarded accounts → entry + postings insert → balance projection update → `ledger.entry.posted` outbox append.
- `application/transaction-history.projector.ts` — idempotent async projection of `ledger.entry.posted`.
- `ledger.module.ts` — DI bindings for `LedgerStore`, `PostingService`, `TransactionHistoryProjector`.

**Identity** (`apps/api/src/modules/identity`), **KYC** (`apps/api/src/modules/kyc`)
- Wave A: `users` (unique lower-cased email), `email_verifications` (hashed codes), `RegistrationService` (user + code + KYC application; `kyc.approved` outbox event on approval), mock `KycPort` (`KYC_PORT` token, `kyc.module.ts`).
- Wave B (ADR-0020): `credentials`, `sessions` (hashed opaque access/refresh, rotation with reuse detection, idle/absolute deadlines), `devices`, `webauthn_challenges` (hashed, single-use, typed), `enrolment_tokens`; `WebAuthnService` (UV required, attestation `none`, decoys for unknown emails, counter-regression rejection); `SessionService` (issue/validate/refresh/revoke).
- Wave C (ADR-0021):
  - `EmailVerificationService` re-keyed by **email** — `verifyEmail(email, code)` returns `{ userId, enrolmentToken }` with uniform failures; `resendVerification(email)` silently re-delivers codes to passkey-less users (the enrolment-token re-issue path).
  - `SessionService.listSessions(userId)` — active sessions joined to devices, no token material.
  - SCA seam: `application/sca-grant.ts` (`ScaAction`, `computeActionHash` over `shared/crypto/canonical.ts` stable stringify, `issueScaGrant`, **`consumeScaGrant`** — the call Slice 5 makes inside the posting transaction) and `WebAuthnService.startStepUp`/`finishStepUp` (ceremony type `sca`, `action_hash` on the challenge, single-use `fsg_` grant bound to user + session + action, 5-min TTL). Schema: migration `0006` (`sca` enum value, `webauthn_challenges.action_hash`, `sca_grants`).
  - `application/identity-sweeper.ts` — ADR-0021 retention (prompt purge of dead secrets; 90-day grace for dead sessions; grants swept before sessions for the FK).
  - HTTP: `http/auth.controller.ts` (register, verify-email, resend-verification, WebAuthn registration/authentication options+verify, refresh; per-route throttles; optional-bearer resolution for additional passkeys), `http/sessions.controller.ts` (logout, list, revoke — `SessionAuthGuard`), `http/sca.controller.ts` (options, verify — guarded), `http/dtos.ts` (nestjs-zod DTOs), `identity.module.ts` (factories + module-scoped `ThrottlerModule` with `skipIf` kill-switch).

**Accounts** (`apps/api/src/modules/accounts`) — Slice 4, ADR-0022
- `infra/accounts.schema.ts` — `accounts` (one per user: unique `user_id`) and `wallets` (one per currency per account; unique 1:1 `ledger_account_id` binding). Migration `0007`. No balance column: balances are read from the ledger projection.
- `application/account-provisioning.service.ts` — the `kyc.approved` outbox handler. Runs **inside the dispatcher transaction**; creates the account, wallet, and backing ledger account (`wallet:<walletId>`, liability) atomically with the dispatch marker. Idempotent via insert-first `ON CONFLICT (user_id) DO NOTHING` (redelivery short-circuits before any ledger account is created — no orphans).
- `application/account.service.ts` — read side: `listAccounts` (principal-scoped) and `getAccount` (ownership-asserted); each wallet's live balance comes from `LedgerStore.getBalance`.
- `http/accounts.controller.ts` — `GET /v1/accounts`, `GET /v1/accounts/:accountId` (`SessionAuthGuard`, `CurrentPrincipal`, explicit `ZodValidationPipe`). `accounts.module.ts` binds the services by factory and exports `AccountProvisioningService` for the dispatcher.
- Enabling change: `LedgerStore.createAccount` takes an optional `executor` (enlist in a caller's tx, like `SessionService.issueSession`); `kyc.approved` now has a typed payload in `kyc/application/kyc-events.ts`.
- Slice 5 additions: `application/wallet-resolver.ts` (`WalletResolver` — resolve the caller's primary EUR wallet, resolve a recipient by email, and resolve an owned wallet for the history read to its `ledger_account_id`, all ownership-aware; the `ledger_account_id` never leaves the module) and `http/wallets.controller.ts` (`GET /v1/wallets/:walletId/transactions`, ownership-scoped, cursor-paginated). Both exported/wired in `accounts.module.ts`.

**Payments** (`apps/api/src/modules/payments`) — Slice 5, ADR-0023 (funding re-targeted in Slice 7, ADR-0025)
- `application/transfer.service.ts` — `TransferService`: validates and resolves sender/recipient EUR wallets, rejects self-transfer and non-EUR, recomputes the action hash from the **executed** amount+payee via the shared `buildTransferScaAction` (never from a client action), and posts `Dr sender / Cr recipient` (sender guarded) through `PostingService.post`, consuming the single-use grant in the posting transaction via the new `onClaimed` hook. Idempotency: `actorId=userId`, `key=Idempotency-Key`, fingerprint over `{recipient, amount, currency}` (grant excluded).
- `application/funding.service.ts` — `FundingService`: `Dr system:settlement / Cr target-wallet` (unguarded settlement) via `PostingService.post`. Since Slice 7 it takes an explicit **target wallet** and an **admin actor** rather than crediting the caller, has no kill-switch (authorization is role + four-eyes + audit), and exposes `validateRequest` — the single place the amount and target rules live, called both when a four-eyes request is filed and when it executes. An optional `onAuthorize(tx, now, entryId)` hook runs inside the posting transaction before any ledger write; the admin approval transition rides it. `ensureSystemAccount` lazily creates `system:settlement`. **No HTTP surface of its own** — reached only through the admin four-eyes workflow.
- `http/transfers.controller.ts` (`POST /v1/transfers`), `http/idempotency-key.ts` (required-header helper → 400 if missing), `http/dtos.ts`. `payments.module.ts` binds the services by factory with explicit `@Inject` tokens and a module-scoped throttler (same `THROTTLE_ENABLED` kill-switch), and exports `FundingService`; registered in `app.module.ts` and `openapi/build-document.ts`.
- Ledger enabling change: `PostEntryCommand` gained an optional **`onClaimed(tx, now)`** hook that `PostingService.post` runs after a successful idempotency claim and before any ledger write — so the SCA grant is consumed exactly once (replays skip it) and atomically with the post. New `application/transaction-history.reader.ts` (`TransactionHistoryReader`, keyset pagination) backs the wallet history endpoint; both wired in `ledger.module.ts`. No new migration (every table already existed).

**Audit** (`apps/api/src/modules/audit`) — Slice 6, ADR-0024
- `infra/audit.schema.ts` — `audit_log`: an append-only, hash-chained trail (migration `0008`; the ledger's `fides_forbid_mutation` triggers reject UPDATE/DELETE). Columns: `seq` (gap-free), `actor_type`/`actor_id`, `action`, `resource_type`/`resource_id`, `before`/`after` (jsonb), `correlation_id`, `metadata`, `prev_hash`, `hash`, with unique indexes on `seq`/`prev_hash`/`hash` as anti-fork guards.
- `application/audit.service.ts` — `AuditService.append(executor, input)` takes the caller's transaction, acquires a transaction-scoped advisory lock, links to the tail (`hash = sha256(prev_hash + stableStringify(core))`, `occurredAt` hashed as epoch ms), and inserts. Pure `verifyAuditChain(rows)` + a `verify()` reader confirm integrity (the reconciliation analogue). `application/audit-actions.ts` centralizes the action/resource constants.
- `audit.module.ts` — binds `AuditService` by factory (a dependency leaf: db, ids, clock); imported by identity, accounts, and payments (no cycles).
- Wiring seams: the transfer and funding append via a new symmetric **`onPosted(tx, now, result)`** hook on `PostEntryCommand` (mirror of `onClaimed`, run after all ledger writes, first-execution-only so an idempotent replay adds no record); `WebAuthnService.finishStepUp`, `SessionService.revokeSession` (now wrapped in a transaction) and the `refresh` reuse branch, and `AccountProvisioningService` (a `system` actor, inside the dispatcher tx) append in their existing transactions. Each controller threads the correlation id onto its command.
- Retention change: `IdentitySweeper` now purges dead sessions promptly (no 90-day grace); the SCA-grant→session FK is `ON DELETE CASCADE` (migration `0009`) so a purged session takes any outstanding grant with it. Records hold internal references only — no raw PII.

**Admin** (`apps/api/src/modules/admin`) — Slice 7, ADR-0025
- `infra/admin.schema.ts` — migration `0010`: `admins` (role enum, scrypt `password_hash`, plaintext `totp_secret`, `totp_enrolled_at`, `last_totp_step` replay guard, status), `admin_sessions` (hashed token, sliding `idle_expires_at`, hard `absolute_expires_at`), `admin_login_challenges` (the hashed post-password intermediate, with `secret_issued_at` for once-only enrolment), and `pending_admin_actions` (generic type + jsonb payload, maker/checker, status, expiry, `result_ref`, plus a `CHECK (checker_id <> maker_id)`). Same migration adds `'admin'` to the `audit_actor_type` enum.

- `application/admin-auth.guard.ts` — `AdminAuthGuard` (reuses only the pure `extractBearerToken`), `RequirePermission`, and `AdminPermissionGuard`, which **fails closed** if a route declares no permission or no admin is attached.
- `application/admin-read.service.ts` — customer list/detail, `resolveWalletLedgerAccount`, `getLedgerAccount` (projection vs. recomputed sum + `reconciled`), `listAuditRecords` (keyset over `seq`, filterable), `verifyAudit` (whole chain from genesis, deliberately not range-scoped). ### Slice 7 — Admin RBAC + MFA + four-eyes — DONE (this session, ADR-0025)

All four delegated calls agreed on 2026-07-13 were honored: admin foundation + read-only views + admin-action auditing **plus** maker-checker proven end to end on admin funding (breadth deferred to Phase 2/3); a separate `admins` entity with `AdminAuthGuard`/`AdminPrincipal` and its own session table; password + TOTP rather than passkeys; and the dev faucet retired. So were the finer calls: scrypt via `node:crypto`, an in-house RFC 6238 TOTP tested against the RFC vectors, the five-role enum with a code-defined matrix behind `@RequirePermission`, a generic `pending_admin_actions` table with one registered type, the deferred audit read + verify behind `auditor`-or-higher, env bootstrap only when no admin exists, and a 30-min idle / 8-h absolute session. Assist mode stayed deferred to Phase 2.

Three decisions were taken during the build that §5 did not settle:
- **Session shape:** a single opaque sliding-idle token, not an access/refresh pair. Rotation exists to keep a 90-day customer session safe behind a short access token; at a 30-minute idle window the sliding deadline already is that, so a refresh endpoint would add a token and a protocol for nothing.
- **SoD read literally:** `super_admin` holds every permission **except** `admin_funding.request`, so no role holds both halves of the pair — ADR-0011's "no single role can both initiate and approve" as written rather than approximated. A matrix-wide unit test locks it in.
- **A staffing surface was added** (`POST/GET /v1/admin/admins`, `POST /v1/admin/admins/{id}/status`, behind a new `admins.manage` held by `super_admin` alone). This was not in the agreed scope, but seeding creates exactly one admin and the matrix denies that admin the maker half — so without it the four-eyes workflow is unstaffable outside tests, and the slice's headline control could not be operated in any real environment.

One further correction worth remembering: `approve` deliberately performs **no pre-flight status check**. An earlier version did, and it rejected a checker's retry carrying the original `Idempotency-Key` with a 400 — exactly the case idempotency exists for. The authoritative checks run once, under `FOR UPDATE`, inside the posting transaction, which an idempotent replay never enters.

Decisions taken with the user on 2026-07-29 that govern the remaining waves: **`apps/admin` stays a shell** (roadmap puts admin UI in Phase 2; Phase 1 exit criteria do not need it); `packages/ui-*` grows only to what the flows need, with **no Radix/shadcn** so the dependency surface stays flat after ADR-0026; and the **Playwright spec walks the full exit criteria** — register, verify, enrol passkey, sign in, balance, transfer by email through the SCA step-up, balance moved and history row — with WebAuthn driven by the CDP virtual authenticator. E2E lives in its own workspace package and runs as a **separate CI job**, so the fast verify job stays fast.
- **Wave B (web client) is done.** Seven screens covering the exit criteria, on the ADR-0027 cookie transport. `@simplewebauthn/browser` taken (zero transitive dependencies, already matching the server's major); `next-intl` rejected as too much surface immediately after ADR-0026, so i18n is a typed catalogue behind a provider and a hook. Money is formatted with exact `BigInt` arithmetic and handed to `Intl` as a decimal string — never through `Number`, because a balance can exceed `MAX_SAFE_INTEGER` and silently rounding one in the UI is not an acceptable failure for a ledger. The enrolment token travels between verification and passkey creation in `sessionStorage`, not the URL: it authorizes the account's first passkey, and a query string writes that into history and the address bar.
- **Wave C (mobile client) is done.** Eight screens, native passkeys via `react-native-passkeys`, tokens in the platform keystore via `expo-secure-store` — mobile stays on **bearer**, since the cookie mode exists for browsers that cannot hold a token away from script. Both new dependencies have zero transitive dependencies; `expo-router` was rejected (roughly twenty packages for eight linear screens), so routes are a discriminated union. The refresh path is **single-flighted**, which is load-bearing rather than an optimization: rotated refresh tokens trip reuse detection, so two concurrent 401s would revoke a legitimate user's session. Passkeys bind to a domain at build time, so it enters through `app.config.ts` from the environment — see `docs/mobile-passkeys.md` for the online and local paths and why `localhost` cannot work for native passkeys.
- **`@fides/i18n` is new** and holds what both clients say and how they format it: catalogue, interpolation, locale negotiation, and the money helpers that used to sit in `@fides/ui-web`. Each app keeps its own React binding. Duplicating a translation catalogue across two clients of one product is drift waiting to happen.
- **Wave D (end-to-end) is done, and it earned its keep immediately.** `apps/e2e` drives the built API and web app against a Testcontainers Postgres through a real Chromium, with genuine WebAuthn ceremonies on the CDP virtual authenticator. Its first complete run found a **real bug in ADR-0027**: the CSRF cookie was path-scoped to `/v1`, but `document.cookie` exposes only cookies whose path prefixes the *document's* path, and the web client is served from `/en/...`. The readable half of the double-submit pair was unreadable by the only code that echoes it, so every state-changing request in cookie mode returned 403. Fixed to `Path=/` (the token carries no authority alone; the credentials keep their scoping) and now asserted on both the set and the clear. **No supertest-based test could have caught it** — supertest sends whatever `Cookie` header the test builds and has no notion of path scoping.
- **Two pre-existing defects in the Phase 0 mobile shell** surfaced in Wave C, because it had never actually been bundled: `@babel/runtime` was not a declared dependency, and `metro.config.js` set `disableHierarchicalLookup`. That setting is the standard advice for npm and yarn monorepos, where everything is hoisted flat; pnpm's layout is the opposite, keeping a package's dependencies as siblings inside its own directory, so walking up is exactly what resolves them. With it on, no transitive native module resolved at all.

## 6. Environment & workflow notes

- **Node 22, pnpm 9.12.3 via Corepack.** `pnpm` is **not on PATH** — invoke as `corepack pnpm ...`.
- **Turbo root scripts fail locally** ("cannot find pnpm binary"); run per package: `corepack pnpm --filter @fides/api <script>`. CI is unaffected.
- **`pnpm test` requires Docker** (Testcontainers Postgres, committed migrations applied). Test files run serially (`fileParallelism: false`) because they truncate a shared database.
- **DI/validation convention (important):** the vitest esbuild transform emits no `design:paramtypes`, so type-only injection silently yields `undefined` in tests. Every Nest-instantiated class (controllers, guards, schedulers) uses **explicit `@Inject(Token)`** constructor parameters, and every `@Body`/`@Param` carries an **explicit `new ZodValidationPipe(Dto)`** (the global pipe stays as a production safety net; the contracts' transforms are idempotent). Follow this for all new HTTP surface.
- **Contracts build:** `apps/api` consumes `@fides/contracts` from its built `dist` — after editing contracts run `corepack pnpm --filter @fides/contracts build` before typechecking the API.
- **Git pre-commit hook** runs `pnpm exec lint-staged`; prefix commits with the Corepack shim: `PATH="$HOME/.corepack-shims:$PATH" git commit ...`.
- **Migrations** are generated offline: `corepack pnpm --filter @fides/api exec drizzle-kit generate --name <name>` (latest: `0010_admin_rbac`). Slice 6 added `0008_audit_log` (with hand-appended append-only triggers — drizzle-kit does not emit them, same as `0002`) and `0009` (the SCA-grant→session FK cascade). Slice 7 added `0010_admin_rbac`, which needed **no hand-editing**: drizzle-kit emitted the `CHECK` constraint from the schema's `check()` helper, and `ALTER TYPE … ADD VALUE 'admin'` runs fine inside the migrator's transaction on Postgres 12+ (the new value is only *used* in later migrations). New env vars are documented in `.env.example` (WebAuthn, session TTLs, CORS, throttle/scheduler switches and intervals, and the `ADMIN_*` settings).
- **`test/db.ts` `resetDb` must list every table.** Adding a table without adding it to the TRUNCATE list leaves state bleeding between tests. Slice 7 added `pending_admin_actions`, `admin_login_challenges`, `admin_sessions`, `admins`. (Slice 8's migration `0011` adds a *column* to `sessions`, not a table, so the list is unchanged.)
- **Two transports on the customer surface (ADR-0027).** `SessionAuthGuard` prefers `Authorization: Bearer` and only falls back to the access cookie when the header is absent; a *malformed* bearer is rejected rather than retried as a cookie. Any new state-changing route inherits the CSRF check automatically through the guard — but a route deliberately placed **outside** the guard (as `/v1/auth/refresh` is, because it runs on an expired access token) must enforce CSRF itself, as refresh does inside its rotation transaction. Check this when adding unguarded state-changing routes.
- **Admin test helpers** live in `test/admin.ts`: `seedAdmin` (inserts directly with cheap scrypt parameters — the production defaults cost ~100 ms a hash) and `signInAdmin` (drives the real two-step HTTP login, enrolling TOTP when needed). Note the TOTP replay guard: signing the *same* admin in twice inside one 30-second step needs an advanced `atMs`.
- **Repo is PUBLIC** (`LorenzoCianfe/fides`); Dependabot tuned on `main`; framework majors deferred to Phase 7.
- **Patched dependencies (ADR-0026).** `patches/brace-expansion@5.0.9.patch` (bumped from `5.0.8` on 2026-08-06 for `GHSA-rgw5-rvv9-x895`; see the ADR addendum) is applied through `pnpm.patchedDependencies` and must be kept in sync with the exact-version override in the root `package.json`. pnpm 9 keys patches by exact version, so bumping the override without regenerating the patch fails the install loudly — which is the intended behaviour, not a bug to work around. Regenerate with `corepack pnpm patch brace-expansion@<version>` then `corepack pnpm patch-commit <dir>`. Audit overrides are keyed on the advisory's vulnerable range (`"postcss@<8.5.18": ">=8.5.18"`), never a bare package name, so they cannot silently upgrade an unrelated major line; `security.md` §9.1 has the remediation order.
- **Commit cadence:** per-slice conventional commits on a feature branch, then a PR to `main`. CI and CodeQL only run on `main` pushes and PRs **targeting** `main`, so work must reach `main` through a PR to be gated before it lands. The Slice 1–7 backend landed this way at the end of Slice 7; Slice 8 branches from `main`.

## 8. Known gaps / watch-items

- ~~Token transport on web is body-only~~ — **closed in Slice 8 Wave A (ADR-0027).** An opt-in, per-request cookie transport (`X-Fides-Token-Transport: cookie`) withholds the tokens from the body and sets them `httpOnly`/`SameSite=Strict`, with the refresh cookie scoped to `/v1/auth/refresh`. Bearer stays the default and is untouched, so mobile and every pre-existing test are unaffected. **Two things to know:** `SameSite=Strict` requires the web client and API to be **same-site** (ports/subdomains fine, different registrable domains not — such a deployment needs `SameSite=None`, where the CSRF token becomes the only defence); and a session issued in bearer mode carries no CSRF hash, so it can never be driven from a cookie — the check fails closed, which is deliberate.
- ~~Security headers (helmet/HSTS) not yet applied~~ — **closed in Slice 8 Wave A (ADR-0027).** Two-year HSTS with preload, `default-src 'none'` on the JSON surface, the Swagger relaxation scoped to `/docs` alone, `Cross-Origin-Resource-Policy: cross-origin` (CORS is the real control for a cross-origin JSON API), and credentialed CORS with an explicit request-header allowlist.
- **Native passkeys are implemented but not verified on a physical device.** The API serves `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` from config, so the association follows whichever HTTPS origin fronts it — set `IOS_APP_ID`/`ANDROID_PACKAGE_NAME`/`ANDROID_CERT_FINGERPRINTS`, point an HTTPS tunnel at the API, and set `WEBAUTHN_RP_ID` plus `WEBAUTHN_ORIGINS` to that host. `localhost` will not work on device: a platform authenticator requires a real HTTPS relying-party id. Document shape and routing are covered by tests; the on-device ceremony is not, and cannot be from CI.
- **Throttle counters are in-memory** — reset on restart, per-instance only; storage seam ready for Redis if topology changes.
- **Registration 409 remains an enumeration channel by design** (throttled; ADR-0021).
- ~~Dev funding faucet~~ — **closed in Slice 7 (ADR-0025).** `POST /v1/dev/funding` and `DEV_FUNDING_ENABLED` are gone; funding is admin-only behind four-eyes, and a customer cannot credit their own wallet by any route.
- **Admin TOTP secrets are stored unencrypted** (ADR-0025). Every other secret in the system is stored only as a hash, but TOTP verification needs the secret itself. Accepted interim gap until field-level/KMS encryption exists (`security.md` §6.2); bounded to the second factor of a few back-office accounts whose first factor is separately scrypt-hashed, and the first candidate for field-level encryption when it lands.
- **No admin password rotation, self-service password change, or TOTP reset.** An operator who loses their authenticator needs direct database intervention. Acceptable at this size; the first gap to close if the back office grows. A `super_admin` can disable and re-create an account as a workaround.
- **Admin login is throttled but not lockout-protected.** The five-minute login challenge accepts repeated TOTP attempts (a wrong code rolls back so a typo does not cost the password step), bounded only by the route throttle. At 10 attempts/minute against a six-digit code with a ±1-step window the odds are negligible, but per-account lockout and failed-attempt alerting are Phase 2 hardening.
- **Denied admin actions are not audited**, consistent with ADR-0024: a denial rolls its transaction back, so it cannot be captured atomically. A rejected *approval* is recorded (it is a committed decision); a failed sign-in is not.
- ~~CI's dependency audit is failing on `main`~~ — **closed 2026-07-29 (ADR-0026).** The gate exits zero again. Three things the earlier entry got wrong, corrected here because they shaped the fix: `postcss` had joined the advisory set (two highs) and was not in the original list; `sharp` enters through `next`, not Expo; and "none are reachable from `apps/api`" is **false for `js-yaml`**, which arrives via `@nestjs/swagger@7.4.2`, a production dependency of the API (unexploitable in practice — Swagger serializes the OpenAPI document, it never parses attacker YAML — but the claim did not hold). What remains open, all deliberately: **`@nestjs/core`** (moderate) is patched only in `>= 11.1.18`, a Nest 10→11 major belonging to Phase 7; the **`lodash` suppression** (`GHSA-r5fr-rjxr-66jc`) stays because its patch target `lodash >= 4.18.0` was never published; and the **`brace-expansion` patch is live maintenance debt** — it can be deleted once the Expo toolchain stops pulling `glob@7`/`rimraf@3`, which is what drags in the `minimatch@3` that needs the shim. Note that pnpm counts suppressed advisories in its summary tally but excludes them from the exit code, so the gate reports "1 high" while passing: **read the exit status, not the count.**
- The bootstrap admin is created at application boot from `ADMIN_BOOTSTRAP_*`. Because the HTTP test suites truncate between tests, they re-seed operators themselves — a boot-time seed is not a fixture to rely on.
- **The transfer route exposes a throttled recipient-existence oracle** (an unknown recipient email is a 404), accepted as consistent with the registration-409 posture and mitigated by mandatory SCA + throttling; superseded when public payment handles (`@tag`) replace email as the P2P identifier (roadmap Phase 2). ADR-0023.
- Redis is still unused (sessions/challenges/idempotency are Postgres-backed; any Redis fast-path must preserve immediate revocation, ADR-0020).
- Device metadata is client-declared and untrusted until mobile attestation (Slice 8).
- WebAuthn **server-issued options schemas** in contracts are documentation-shaped (responses are not runtime-validated); client-submitted payloads are validated with `.passthrough()`.
- **Account provisioning is asynchronous:** a just-approved user has no account until the outbox dispatcher runs (`GET /v1/accounts` returns an empty list until then, never an error). With `SCHEDULERS_ENABLED=false` (the HTTP test topology), drive it explicitly via `app.get(OutboxDispatcher).dispatchPending()`.
- The `GET /v1/accounts/:accountId` route returns **403** (not 404) for an account owned by another user — a deliberate, minor existence oracle kept for consistency with `assertResourceOwnership`; account ids are non-enumerable UUID v7 (ADR-0022).
- **Audit trail (ADR-0024):** the chain detects any modification or removal of a non-tail record, but not deletion of the **tail** (truncation) — that needs an external high-water anchor, deferred beyond Phase 1. Denied/failed sensitive attempts are not recorded (a denial rolls its transaction back; a tamper-evident denial log is a separate out-of-band concern). The read/verify surface arrived in Slice 7 (`GET /v1/admin/audit`, `/verify`, behind `audit.read`). The system, outbox-driven provisioning record carries a null correlation id (the dispatcher passes only the payload), traced instead by `userId` + KYC reference.
