# ADR-0025: Admin identity, RBAC, MFA, and four-eyes on admin funding

- Status: Accepted
- Date: 2026-07-27
- Deciders: Solo maintainer
- Refines: [ADR-0011](0011-admin-rbac-four-eyes.md)
- Relates to: [ADR-0020](0020-session-tokens-webauthn-policy.md), [ADR-0021](0021-http-auth-surface-policy.md), [ADR-0023](0023-p2p-transfer-sca-enforcement-dev-funding.md), [ADR-0024](0024-append-only-hash-chained-audit-trail.md)

## Context

ADR-0011 mandates granular RBAC, segregation of duties, four-eyes on high-risk operations, mandatory admin MFA, and shorter admin sessions. `roadmap.md` scopes the Phase 1 admin slice more narrowly, as "read-only user/account and ledger views", and defers the high-risk admin actions ADR-0011 names — account suspension, fund reversal, limit override, KYC override — to Phase 2/3, where those actions first exist. Slice 6 (ADR-0024) deliberately shipped the audit trail with no read or verify surface, on the grounds that reading it is an administrative capability that must wait for the auditor role defined here. Slice 5 (ADR-0023) shipped a self-service dev funding faucet as a stopgap, recorded as a known gap to be closed by an admin-only, four-eyes funding operation.

What was open: how admin identity relates to customer identity; what authentication factors the back office uses given that the customer stack is passkey-only and its WebAuthn relying party is coupled to `users`/`credentials`; the shape and lifetime of an admin session; how roles map to permissions and how segregation of duties is expressed; whether four-eyes is built generically or for one action; which read surfaces land; and what becomes of the faucet.

The reconciliation adopted here is to **build the admin foundation in full and prove maker-checker end to end on the one genuinely sensitive admin action that exists in Phase 1** — admin funding. Four-eyes *breadth* is deferred with the actions it would govern; four-eyes *machinery* is not deferred, because a workflow that has never executed a real state change is not evidence that the control works.

## Decision

**Admin identity is a separate entity, not a role on `users`.** A distinct `admins` table carries its own credentials, role, and lifecycle, with an `AdminAuthGuard`, an `AdminPrincipal`, and a dedicated session table. Customer and admin authentication share no table, no guard, and no token namespace. The alternative — a role column on `users` — was rejected because it makes every customer-facing authorization path one missing predicate away from privilege escalation, gives an attacker who compromises a customer session a foothold in the same identity record, and entangles the customer lifecycle (KYC status, suspension, account provisioning on approval) with back-office access. Concretely, `assertResourceOwnership` remains customer-only: admin authorization is permission-based, never ownership-based, and the two must not be able to satisfy each other's checks. The cost is deliberate duplication of the session mechanics, accepted as the price of a hard isolation boundary.

**Admin authentication is password + TOTP, not passkeys.** This is a deliberate divergence from the customer stack (ADR-0007/0020: passkey-only, no passwords). The relying party built in Slice 3 Wave B is coupled to `users` and `credentials` — challenges reference `users.id`, credentials hang off users, and the ceremonies resolve subjects by customer email — so reusing it for admins would mean either giving admins customer rows (rejected above) or a parallel WebAuthn implementation, which is far more machinery than a back office of a handful of operators needs in Phase 1. Password + TOTP is two independent factors (knowledge + possession), satisfies ADR-0011's mandatory-MFA requirement, and keeps the back office isolated from the customer authentication machinery. Passwords are hashed with **scrypt** from `node:crypto` (N=2^15, r=8, p=1, 16-byte salt, 64-byte key), stored as a self-describing `scrypt$N$r$p$salt$hash` string so parameters can be raised without a migration, and compared with `timingSafeEqual`. Argon2id is noted as later hardening; it needs a native dependency that `node:crypto` does not provide, and scrypt is a memory-hard, standardized KDF that is not the weak link at this stage. Admin passkeys are the correct long-term answer and are recorded as the migration path once the relying party is decoupled from `users`.

**TOTP is a minimal RFC 6238 implementation on `node:crypto`, not a dependency.** HMAC-SHA1, 6 digits, a 30-second step, and a ±1-step acceptance window, with base32 secret encoding and an `otpauth://` provisioning URI. It is roughly a hundred lines over `crypto.createHmac`, and it is unit-tested directly against the test vectors in RFC 6238 Appendix B, which is stronger evidence of correctness than a dependency's reputation. Replay within the acceptance window is prevented by a `last_totp_step` column: a code is rejected unless its time step is strictly greater than the last accepted one, so a code observed in transit cannot be reused even inside its validity window.

**Enrolment happens at first login, and the secret never touches configuration.** Login is two-step. `POST /v1/admin/auth/login` verifies the password and returns a short-lived (5-minute), single-use, hashed opaque **login challenge token** — not a session — together with an `mfaEnrolled` flag. If the admin is not yet enrolled, that token may be exchanged exactly once at `POST /v1/admin/auth/mfa/enrol` for a freshly generated secret and its provisioning URI; the secret is stored but not activated. `POST /v1/admin/auth/mfa/verify` checks the code and, on success, activates the enrolment (first time) and issues the admin session. No session exists until both factors are satisfied. The alternative of seeding the secret from the environment was rejected: it puts a long-lived shared secret in `.env`, and it gives no enrolment path for admins created later.

**The admin session is a single opaque token with a sliding idle window.** 256 bits of randomness, stored only as a SHA-256 hash on an `admin_sessions` row — the ADR-0020 pattern, so revocation is immediate — with a **30-minute idle deadline slid forward on each validated request and a hard 8-hour absolute cap** (both env-tunable). The customer stack's access/refresh pair with rotation and reuse detection was deliberately not mirrored: that machinery exists to keep a long-lived (90-day) session safe with a short-lived access token, and at a 30-minute idle window the idle deadline *is* the sliding window, so a refresh endpoint would add a second token, a rotation protocol, and a reuse-detection branch to buy nothing. The token carries an `ast_` prefix so it is never confused with a customer `fat_` token, and admin tokens live in a different table, so a customer token presented to an admin route fails at lookup rather than at a status check.

**Roles map to permissions through a code-defined matrix, and segregation of duties is a property of that matrix.** The five ADR-0011 roles (`super_admin`, `compliance_officer`, `fraud_analyst`, `support_agent`, `auditor`) are an enum; a single `PERMISSIONS_BY_ROLE` table in code maps each to an explicit permission set, enforced by a `@RequirePermission` guard. An admin holds exactly one role in Phase 1 — multi-role admins would need a union-of-permissions resolution and add nothing when the back office is this small. The matrix lives in code rather than in the database because it is a policy invariant, not operational data: it is reviewable in diffs, testable, and cannot be silently widened by a privileged SQL statement.

Segregation of duties is enforced **structurally, in the matrix itself**: `admin_funding.request` is held by `support_agent` and `compliance_officer`; `admin_funding.approve` is held by `super_admin` alone; and `super_admin` — which holds every other permission — is deliberately **denied** `admin_funding.request`. No role therefore holds both halves, which is ADR-0011's "no single role can both initiate and approve" read literally rather than approximated. A unit test asserts this as an invariant over the whole matrix, so a future permission added to `super_admin` out of convenience fails the build rather than quietly collapsing SoD. The runtime `checker_id != maker_id` check is retained as belt-and-braces: it defends against the case where two admins share a role and against any future matrix that is less strict.

**Four-eyes is a generic pending-action table with exactly one registered type.** `pending_admin_actions` holds a type discriminator, a jsonb payload, maker and checker identities, a status, an expiry, and a reference to whatever the execution produced. Exactly one type — `admin_funding` — is registered, with a typed payload validator and an executor. The generic table with one type was chosen over a purpose-built `funding_requests` table because the schema and workflow generalize to the Phase 2/3 actions (suspension, reversal, limit override) at no extra cost today, and over a full plugin registry because one registered type does not justify the indirection. Approval executes the action **inside the same transaction that transitions the row to `approved`**, conditionally on the row still being `pending` — the same atomicity principle as ADR-0019 and ADR-0024 — so a concurrent double-approval cannot execute twice, and an execution failure rolls the approval back rather than leaving an approved-but-unexecuted request. Requests expire after 24 hours; an expired request cannot be approved.

**The dev funding faucet is retired and its posting path is re-targeted, not duplicated.** `POST /v1/dev/funding` and the `DEV_FUNDING_ENABLED` kill-switch are removed, closing the ADR-0023 known gap. The money-movement logic stays where the ledger integration lives: `FundingService` keeps the settlement account, the balanced entry, idempotency, and the audit append, but now takes an explicit **target wallet** and an **actor** rather than crediting the caller from their own session. The kill-switch is gone because the operation is no longer an unauthenticated-by-design affordance — it is authorized by role, by four-eyes, and by audit — while the per-request cap is retained as a blast-radius limit and renamed `ADMIN_FUNDING_MAX_MINOR`. The admin module owns the maker-checker workflow and calls into payments; the dependency runs admin → payments, so no cycle is created. Writing a second posting path inside the admin module was rejected: two ways to move money is exactly the duplication that invites divergence in the guard rails.

**Every admin action is audited with `actor_type = 'admin'`.** The `audit_actor_type` enum gains an `admin` value — anticipated by ADR-0024 — in a small enum-alter migration. Session issue, session revocation, MFA enrolment, funding request, approval (carrying the executed journal-entry id), and rejection are all appended through the existing `AuditService.append` inside their own transactions; the funding execution rides the `onPosted` hook already built for the money path. Bootstrap seeding of the first admin is audited as a `system` actor, since no admin exists to attribute it to. Admin records, like customer ones, carry internal references only.

**The read surface is four views behind role-appropriate permissions.** Customer list and detail (`GET /v1/admin/customers`, `/{userId}`) with KYC status, accounts, wallets, and live balances; wallet transaction history (`GET /v1/admin/wallets/{walletId}/transactions`), the same keyset-paginated read customers get but admin-scoped instead of ownership-scoped; the audit read and verification deferred from Slice 6 (`GET /v1/admin/audit`, `/verify`), behind `auditor`-or-higher; and a ledger view (`GET /v1/admin/ledger/accounts/{ledgerAccountId}`) exposing the projected balance alongside the recomputed sum of postings and an `ok` flag — the ADR-0019 reconciliation invariant made operable rather than test-only. These reads live in an admin-owned read service that queries the tables directly rather than routing through each module's customer-facing service, because those services are ownership-scoped by construction and adding admin bypasses to them would put back-office semantics into the customer authorization path. This mirrors the existing precedent of `WalletResolver` reading the `users` table across a module boundary.

**The first `super_admin` is seeded from the environment, and only when no admin exists.** `ADMIN_BOOTSTRAP_EMAIL` and `ADMIN_BOOTSTRAP_PASSWORD` are consumed at startup by an idempotent seeding step that is a no-op if any admin row is present, so the environment cannot be used to add or reset an admin once the back office is live. The seeded admin has no TOTP secret and must enrol at first login before any session is issued.

**A minimal staffing surface ships with the slice, because four-eyes is not a control that one operator can exercise.** Seeding creates exactly one admin, and the segregation-of-duties matrix denies that admin the maker half — so with seeding alone the funding workflow is unreachable outside tests, and the headline control of this slice would be unstaffable in any real environment. `POST /v1/admin/admins`, `GET /v1/admin/admins`, and `POST /v1/admin/admins/{adminId}/status` are therefore included, behind a new `admins.manage` permission held by `super_admin` alone. A created admin receives a password and no second factor, exactly like the seeded one, and enrols TOTP at first login; creation and status changes are audited. Disabling is the offboarding lever and is immediate — `validateToken` rejects a disabled admin's live sessions on their next request — and an admin cannot disable their own account, so the back office cannot be locked out by a single call. Password *rotation*, admin self-service password change, and TOTP reset are deliberately **not** in scope; they are recorded as known gaps rather than half-built.

**Assist / "view-as-customer" mode is deferred to Phase 2.** ADR-0011 requires it to be explicit, time-boxed, and audited. It is a genuine capability with its own consent, scoping, and expiry semantics, and Phase 1's read views cover the operational need without impersonation. Deferring it keeps this slice's authorization model uniform: an admin acts as an admin, never as a customer.

## Consequences

Positive:

- Customer and admin authentication are isolated at every layer — table, guard, principal, token prefix — so no customer-facing authorization bug can yield back-office access, and `assertResourceOwnership` keeps a single, customer-only meaning.
- Segregation of duties is a structural property of a code-defined matrix and is asserted by a test, not a convention that depends on nobody widening `super_admin` later.
- Four-eyes is proven end to end on real money movement rather than asserted: an admin funding request moves no value until a second, differently-roled admin approves it, and the approval and the posting commit atomically.
- The ADR-0023 gap is closed: the self-service faucet is gone, and its money-movement surface is now gated by role, four-eyes, audit, and a cap.
- Slice 6's deferred audit read and verification surface lands behind exactly the role it was waiting for, making the trail operable without exposing it to customers.
- The pending-action table and its executor registry generalize to the Phase 2/3 high-risk actions with no schema change.

Trade-offs / negative:

- **TOTP secrets cannot be hashed** — verification needs the secret itself — so they are stored in plaintext at rest, unlike every other secret in the system. This is an accepted interim gap until field-level or KMS-backed encryption exists (`security.md` §6.2); it is recorded in the handoff's known gaps, and the blast radius is bounded to the second factor of a handful of back-office accounts whose first factor is separately hashed.
- Passwords re-enter a platform that deliberately has none for customers. The divergence is contained to the admin entity, but it is a second credential model to maintain, and scrypt parameters will need periodic review.
- The admin session duplicates session mechanics rather than reusing `SessionService`. Deliberate, but two implementations of issue/validate/revoke now exist and must not drift.
- `super_admin` is denied a permission, which is surprising for a role named "super". It is documented in the matrix and is the literal reading of ADR-0011; the surprise is preferred to a root role that can self-approve funding across two sessions.
- Four-eyes on funding means a single-operator environment cannot fund a wallet at all, which makes local development and test setup heavier than the faucet was — deliberately, since that friction is the control working. Suites that only need a funded wallet call the funding service directly rather than staffing two admins per fixture; the workflow itself is proven through the real HTTP journey in the admin suite.
- No password rotation, self-service password change, or TOTP reset exists. An admin who loses their authenticator needs direct database intervention, which is acceptable for a back office of this size but is the first gap to close if it grows.
- Admin read views query tables owned by other modules directly, trading a little encapsulation for keeping admin semantics out of the customer authorization path.

## Alternatives considered

- **A role column on `users` instead of a separate entity** — rejected: it makes every customer authorization path one missing predicate away from privilege escalation and entangles the customer lifecycle with back-office access.
- **Passkeys for admins, reusing the Slice 3 relying party** — rejected for Phase 1: the relying party is coupled to `users`/`credentials`, so it would require either admin customer-rows or a parallel WebAuthn implementation. Recorded as the migration path once the relying party is decoupled.
- **An off-the-shelf TOTP library (`otplib`)** — rejected: the algorithm is a hundred lines over `node:crypto` and is directly verifiable against the RFC 6238 vectors, so a dependency adds supply-chain surface without adding assurance.
- **Argon2id password hashing now** — rejected for Phase 1: it needs a native dependency, whereas scrypt is memory-hard, standardized, and available in `node:crypto`. Noted as later hardening.
- **Mirroring the ADR-0020 access/refresh pair for admin sessions** — rejected: rotation exists to make a 90-day session safe with a short access token; at a 30-minute idle window the sliding idle deadline already provides that, and the extra token and protocol buy nothing.
- **Permissions stored in the database** — rejected: the matrix is a policy invariant that belongs in reviewable, testable code, not in operational data that a privileged statement can widen silently.
- **A purpose-built `funding_requests` table** — rejected: the generic pending-action shape costs nothing extra today and already fits the Phase 2/3 actions that four-eyes will govern.
- **Executing the funding after the approval transaction commits** — rejected: it would allow an approved-but-unexecuted request on failure and a double execution under concurrent approval. Execution rides inside the status transition, conditionally on the row still being pending.
- **Enforcing SoD only at runtime (`checker_id != maker_id`), with `super_admin` holding every permission** — rejected as the primary control: it permits one root account to make and approve its own funding across two sessions, which is precisely what ADR-0011 forbids. Retained as a secondary check.
- **Keeping the dev faucet alongside admin funding for test convenience** — rejected: two money-movement paths with different guard rails is the divergence risk the slice exists to remove; tests seed through the ledger directly or through the real four-eyes journey.
- **Building four-eyes breadth (suspension, reversal, card freeze) now** — rejected: those actions do not exist in Phase 1, so the workflow would be built against hypothetical payloads and could not be proven by execution.
